## 3. Schemas

Every schema is a JSON Schema of draft 2020-12 and is itself checked against the published specification by `backlog validate` (4.5).

### 3.1 The base item: [item.schema.json](../2026-11-14-definition-driven-cli/item.schema.json)

An item is one flat JSON object (D-34). [item.example.json](../2026-11-14-definition-driven-cli/item.example.json) fits the schema.

| Property | Required | Given by | Meaning |
|---|---|---|---|
| `seq` | yes | CLI | The item's number in its repository folder; never reused (4.2). |
| `slug` | yes | CLI | The number and the title in file-name form. |
| `title` | yes | person | Short title. |
| `description` | yes | person | What the item is about, in markdown. |
| `team` | no | person | The team that owns the item; absent when it has none (D-29). |
| `repository` | yes | CLI | `owner/name` of the repository the item belongs to. |
| `branch` | yes | CLI | The branch the item belongs to. |
| `created`, `updated` | yes | CLI | Times of creation and of the last change. |
| `updated_by` | yes | CLI | The agent of the command, else the user (4.7). |
| `cli_version` | yes | CLI | The version of the CLI that last wrote the item (D-48, 4.11). |
| `status` | yes | definition | Declared by every item definition; its values come from the definition. |
| `history` | yes | CLI | One entry per change: `at`, `by`, `session`, `command`, `changes` (each changed property with before and after), `note`. Its structure is fixed in the CLI (D-45). |
| any other | no | definition | A field of the definition that applies (4.3). |

### 3.2 The item definition: [item-definition.schema.json](../2026-11-14-definition-driven-cli/item-definition.schema.json)

An item definition is a JSON object whose keys are field names. Each field has a `type` (text, number, boolean, time, person, item, items, list) and may have a `default`, its allowed `values`, the values that are `final` (the item is finished; status only) and a `description`. Every definition declares `status`. No field may take the name of a base property.

There are three places a definition comes from: the `item` of a team in the team file (the team item definition); the file named by `item_definition` in the configuration (the repository's user item definition); and the definition packaged with the CLI (3.7).

### 3.3 The team file and the rule set: [team-file.schema.json](../2026-11-14-definition-driven-cli/team-file.schema.json)

The team file holds one entry per team, each with `people` (each person with a list of role words), `item` (the team item definition, 3.2) and `rules`. Its location is named in the configuration (`teams_file`; default `.backlog/teams.json`). The CLI only reads it (R5).

`rules` is the team's rule set. Its form is [team-rules.schema.json](../2026-11-14-definition-driven-cli/team-rules.schema.json) and its meaning is [team-rules-spec.md](../2026-11-14-definition-driven-cli/team-rules-spec.md): what triggers the rules, how a change is evaluated, the guard form of a rule (`when`, `require`, `error`), the evaluation context (`prev`, `next`, `caller`, `team`, ...), conditions in JsonLogic evaluated by json-logic-js, each kind of rule with examples (transition, field, lock, permission, relation, creation), how rules relate through fields, the queue and filters, error texts, and the validation of the rules. Each team may carry a `description` of its way of working in words (D-56).

### 3.4 The configuration: [config.schema.json](../2026-11-14-definition-driven-cli/config.schema.json)

| Key | Meaning |
|---|---|
| `backlog_repository` | The folder that holds the items, relative to the repository; `.backlog` when they live inside it. |
| `backlog_origin_url` | The address `backlog setup` clones a separate backlog repository from. |
| `user` | The person of the user commands, written by `backlog setup` (git `user.name`, else the login name). |
| `team` | The team a team command acts for when neither flag nor variable names one. |
| `teams_file`, `teams_file_sha` | Where the team file is, and its SHA when last validated. |
| `item_definition` | The repository's user item definition; absent means the packaged one. |
| `archive_folder` | The folder an archived item moves to. |
| `repository_variable`, `branch_variable`, `team_variable`, `agent_variable`, `session_variable` | The names of the environment variables commands read in this repository and branch (D-31, 4.7). |
| `push-backlog-updates` | true by default: the commits the CLI makes are pushed; false keeps them local (D-76). |
| `redact_pii`, `redaction_rules` | Redaction of personal data on or off (default off) and the repository's own redaction rules ([redaction-spec.md](../2026-11-14-definition-driven-cli/redaction-spec.md)). |
| `migrated_at`, `migrated_by_version` | When the items were converted and by which version. |

### 3.5 The index: [index.schema.json](../2026-11-14-definition-driven-cli/index.schema.json)

Per branch, the list of the open items in priority order: number, slug, title and status. The place in the list is the priority; nothing else holds it.

### 3.6 The example team file: [teams.example.json](../2026-11-14-definition-driven-cli/teams.example.json)

Shipped with the CLI in the public repository (D-35) and valid against 3.3. Three teams:

- `simple`: one agent; status todo, doing, done; an estimate and a result; six rules (people only, size on creation, the allowed moves of status, one item doing, done needs a result, archive only done); the queue takes the next todo item.
- `advanced`: a lead and three members; status new, ready, active, checking, closed; holder, checker, parent, dependencies; twelve rules, among them permission rules, a relation rule over the dependencies, a rule counting a member's active items, and a lock on the holder of an active item; the queue gives a member its checks first, then takes ready work for it (setting holder and status in one change).
- `lead-and-reviewers`: a lead, members, a reviewer and an outside reviewer; two reviews counted in a field the reviewer raises, hand-off by the holder, waiting for a decision of the lead; fourteen rules; the queue serves reviewers, members and the lead.

Each team's `description` says its way of working in words. The examples guide (plan, task 12) explains every rule, and shows for each the change it allows and the change it refuses with its text.

### 3.7 The packaged defaults

- [default-item-definition.json](../2026-11-14-definition-driven-cli/default-item-definition.json): `status` with the values new, active and closed, closed final, new by default (D-25 and D-47).
- [default-team.json](../2026-11-14-definition-driven-cli/default-team.json): one team with that definition and five rules: only people of the team act; `new`; `start` (new to active); `close` (active to closed); `archive` (closed only).

- **D-62.** Where a widely used and safe external library does the job, the CLI uses it instead of building its own; building it in the CLI is not allowed then. "Dependency-free" was never a rule that forbids runtime libraries. For this branch: Ajv (with ajv-formats) validates JSON against the schemas, and json-logic-js evaluates the conditions of the team rules; a regular-expression library that matches in linear time is chosen in plan task 9a.

## Session 1: implement (at most 30 minutes)

Work only from this file. Do not read the whole specification; everything this slice needs is above.

1. Load the skills by their installed names: `test-driven-development`, `verification-before-completion`, `systematic-debugging` (only when a test fails for a reason you do not understand), `requesting-code-review`, `ponytail`.
2. Create a local branch from the head of `simplify/pr3-review`: `git switch -c slice/S01 origin/simplify/pr3-review` (after `git fetch`). Do not push.
3. **Scenarios first (BDD).** This slice has no scenario of its own; go to step 4.
4. **Unit tests (TDD).** Write each test of "Unit tests" in the named test file. Run `node --test <that file>`; every new test must fail for the reason the test states. Commit the failing tests: `git commit -m "S01: failing tests"`.
5. **Code.** Write the smallest code that makes the tests and scenarios pass, in the files of "Files" only. An existing test that asserts the old behaviour this slice replaces is updated in the same commit and named in the hand-off; no other file outside "Files" changes. Follow the interfaces exactly (names, parameters, return shapes). Use the libraries named; never hand-build what a library does.
6. **Run.** The slice's test file, then `npm test`, then `npm run check`, then the private-details guard (`node --test .agents/test/no-private-details.test.js` with the deny-list variable the session is given). All pass.
7. **Self review.** Run `requesting-code-review` on your diff against "Requirements" and "Interfaces", then `ponytail` on the same diff: remove every line the tests do not need, every option nobody asked for, every comment that repeats the code. Rerun step 6.
8. **Commit** with the message `S01: Runtime libraries and the schema files` and the repository's agent identity, no trailers.
9. **Hand-off.** Write the hand-off below into the Handoff section of this slice's backlog item.

Stop rules: if 30 minutes pass, or a file outside "Files" must change, or a slice this one depends on is not merged, stop, commit what passes, and write the hand-off with status `BLOCKED` and the reason. Never widen the slice.

## Session 2: review (at most 15 minutes, a new session)

A new session reads only this file and the hand-off in the backlog item.

1. Load the skills: `requesting-code-review` (its reviewer checklist), `ponytail-review`, `verification-before-completion`.
2. `git switch slice/S01`; run the slice's test file, `npm test`, `npm run check` and the guard. Any failure: verdict FAIL.
3. Check, one by one, and write each result:
   - every scenario id of "Scenarios" exists in the named feature file and passes;
   - every test of "Unit tests" exists with that name, asserts what the line says, and passes;
   - every interface exists with the stated name, parameters and return shape;
   - `git diff --stat origin/simplify/pr3-review...` changes only the files of "Files";
   - every line of "Requirements" that the slice touches holds in the code.
4. `ponytail-review` of the diff: anything the tests do not need is a finding.
5. Write the verdict into the Handoff section of the backlog item:

```
REVIEW S01 | verdict: PASS or FAIL
Checks: scenarios <ok/fail>, tests <ok/fail>, interfaces <ok/fail>, files <ok/fail>, requirements <ok/fail>
Findings (FAIL only): <file:line - what is wrong - which requirement or test>
```

A FAIL goes back to session 1 with the findings as its only list. A PASS is merged by the lead.
