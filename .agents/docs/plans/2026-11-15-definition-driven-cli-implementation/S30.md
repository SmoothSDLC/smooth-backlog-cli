## Requirements (copied from the specification)

### 4.6 How a team command applies the rules

Every team command that would change an item builds the change (`prev` and `next`), applies the redaction rules to `next`, checks `next` against the schema and the team item definition with Ajv, then evaluates every rule with json-logic-js. If every rule holds, the change is written with one history entry; otherwise nothing is written, exit 1, and every failing rule's error is returned. `--whatif` evaluates and writes nothing. Commands that only read evaluate no rule. The full specification is [team-rules-spec.md](../2026-11-14-definition-driven-cli/team-rules-spec.md).

### 4.8 Output and exit codes

User commands print text for people; `--json` prints JSON. Team commands print JSON; `--human` prints text for people.

| Exit | Meaning |
|---|---|
| 0 | Succeeded (reading commands and `--whatif` too). |
| 1 | Refused: one line says why; for a team command, every failing rule's error. |
| 2 | Wrong arguments or place; an item, the team file or the configuration cannot be read. |
| 3 | The backlog could not be synchronised, nothing stays changed; for `backlog team pop`, nothing to offer. |
| 4 | The backlog is not set up, or its location is not a git repository. |
| 5 | The item was changed by someone else since the caller read it; nothing written, the item as it is now is printed. |

## 2. The change: what triggers the rules

Every team command that would change an item builds a **change**: the item as it is (`prev`) and the item as it would be (`next`). Every rule is evaluated against every change.

| Command | `command` | `prev` | `next` |
|---|---|---|---|
| `backlog team new` | `new` | `null` | the new item: base properties, the definition's defaults, the given title, description and fields |
| `backlog team update <item> <property> <value>` | `update` | the item | the item with that property set |
| `backlog team archive <item>`, `archive done` (item by item) | `archive` | the item | the item, unchanged |
| `backlog team import`, `branch import` (item by item) | `move` | the item | the item with its new `branch` |
| `backlog team pop` with `take` (9) | `update` | the item | the item with the values of `take` |

Reading commands (`list`, `show`, `query`) make no change and trigger nothing. A change of priority triggers nothing: priority is not a property of the item.

## 10. Error texts

`error` is the text the caller sees. Values may be put in with `{...}` and a path of 5: `{prev.status}`, `{next.estimate}`, `{caller.name}`; a path that cannot be read gives an empty text. A refusal returns every failing rule: in JSON (the default of team commands) `{"refused": [{"rule": "<id or place>", "error": "..."}]}`; with `--human`, one line per failing rule. Exit 1.

- **C-25.** Team commands print JSON by default and text with `--human`.

## Session 1: implement (at most 30 minutes)

Work only from this file. Do not read the whole specification; everything this slice needs is above.

1. Load the skills by their installed names: `test-driven-development`, `verification-before-completion`, `systematic-debugging` (only when a test fails for a reason you do not understand), `requesting-code-review`, `ponytail`.
2. Create a local branch from the head of `simplify/pr3-review`: `git switch -c slice/S30 origin/simplify/pr3-review` (after `git fetch`). Do not push.
3. **Scenarios first (BDD).** This slice has no scenario of its own; go to step 4.
4. **Unit tests (TDD).** Write each test of "Unit tests" in the named test file. Run `node --test <that file>`; every new test must fail for the reason the test states. Commit the failing tests: `git commit -m "S30: failing tests"`.
5. **Code.** Write the smallest code that makes the tests and scenarios pass, in the files of "Files" only. An existing test that asserts the old behaviour this slice replaces is updated in the same commit and named in the hand-off; no other file outside "Files" changes. Follow the interfaces exactly (names, parameters, return shapes). Use the libraries named; never hand-build what a library does.
6. **Run.** The slice's test file, then `npm test`, then `npm run check`, then the private-details guard (`node --test .agents/test/no-private-details.test.js` with the deny-list variable the session is given). All pass.
7. **Self review.** Run `requesting-code-review` on your diff against "Requirements" and "Interfaces", then `ponytail` on the same diff: remove every line the tests do not need, every option nobody asked for, every comment that repeats the code. Rerun step 6.

9. **Hand-off.** Write the hand-off below into the Handoff section of this slice's backlog item.

Stop rules: if 30 minutes pass, or a file outside "Files" must change, or a slice this one depends on is not merged, stop, commit what passes, and write the hand-off with status `BLOCKED` and the reason. Never widen the slice.

## Session 2: review (at most 15 minutes, a new session)

A new session reads only this file and the hand-off in the backlog item.

1. Load the skills: `requesting-code-review` (its reviewer checklist), `ponytail-review`, `verification-before-completion`.
2. `git switch slice/S30`; run the slice's test file, `npm test`, `npm run check` and the guard. Any failure: verdict FAIL.
3. Check, one by one, and write each result:
   - every scenario id of "Scenarios" exists in the named feature file and passes;
   - every test of "Unit tests" exists with that name, asserts what the line says, and passes;
   - every interface exists with the stated name, parameters and return shape;
   - `git diff --stat origin/simplify/pr3-review...` changes only the files of "Files";
   - every line of "Requirements" that the slice touches holds in the code.
4. `ponytail-review` of the diff: anything the tests do not need is a finding.
5. Write the verdict into the Handoff section of the backlog item:

```
REVIEW S30 | verdict: PASS or FAIL
Checks: scenarios <ok/fail>, tests <ok/fail>, interfaces <ok/fail>, files <ok/fail>, requirements <ok/fail>
Findings (FAIL only): <file:line - what is wrong - which requirement or test>
```

A FAIL goes back to session 1 with the findings as its only list. A PASS is merged by the lead.
